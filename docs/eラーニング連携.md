### 3.2.2 なぜ到達度を合成しないのか（E7-c の設計根拠）

本リポジトリの到達度は「講師スコア0.6＋AI採点0.2＋出席0.2」の**週次**値。
先方は「視聴完了率・小テスト正答率・誤答の単元分布・経過日数」からの**単元別**推定値。
**尺度も期間も母集団も違う**ため、加重平均を取っても意味のある数にならない。

さらに先方の受け入れ基準 B-3 が「算出根拠を受講生本人が確認できること。
ブラックボックスにしない」を要求している。合成すると、
**本リポジトリ側の重み付けが先方の説明責任を壊す**（先方は自分の算出根拠しか説明できない）。
並置なら、それぞれのシステムが自分の数値の根拠を説明できる。

> 先方文書はこの点を検討していない（到達度の「返送」としか書かれていない）。
> 合成方針を先に決めておかないと、実装時に相手の想定と食い違う。**E7-c の
> 仕様提示時に「並置する」ことを明示的に伝えること。**

### 3.2.3 残る未決 — 受講生マスタに未成年が入るか

先方 1.3 の対象利用者には中学生・高校生が含まれる。SSOでマスタを共有する以上、
**本リポジトリ側に未成年のデータが載る可能性がある**。

**切り分け**: 「未成年のデータが載る」ことと「未成年が本リポジトリの画面を使う」ことは別。
eラーニングの受講生が触るのはeラーニング側の画面であり、本リポジトリの画面は
教室の対面授業用。**よってUI設計（4章のUI制約・平易な日本語）への影響はない。**
影響は保管するデータに限られる。

入る場合に効くもの:

| 論点 | 影響 | 追加作業 |
|---|---|---|
| **保護者（法定代理人）の同意** | Pマーク（JIS Q 15001）は未成年からの個人情報取得時に保護者同意を求める。マスタの「正」が本リポジトリ側にある以上、同意記録もこちらに要る可能性がある | 規程・申込フロー側が主。DBに同意フラグを持つなら小さなカラム追加 |
| 開示・訂正・削除請求の窓口 | マスタの正がこちらなので請求はこちらに来る | 機能は実装済み（`purgeStudentData`）。運用の割り当てのみ |
| `CLAUDE.md` 9章の記述 | 「対象は成人。未成年前提は誤り」が事実と食い違う | 記述の修正のみ |
| AI講師の出力フィルタ | **追加作業なし** | `src/lib/f2/contentFilter.ts` は元々未成年向け水準（自傷・暴力・武器・薬物・アダルト）で実装され、対象が成人に変わった後も意図的に厳しいまま残してある。マスキング（`masking.ts`）も同様 |
| データの機密性の水準 | **変わらない** | 学習ログは成人でも要配慮データとして扱っており、監査ログの追記専用強制・DBロール分離・氏名の非ログ化・外部API送信前マスキングは既に同一水準 |

**確認先は開発ではなくPマーク管理者と申込フローの設計者**（未決事項 #13・#10）。
確定していなくても E7 の実装は着手できる。

## 4. 見落としやすい副作用

### 4.1 同一サーバーの共有（先方 3.1）

先方は「発注者が契約する**さくらのクラウド**。クラウドキャンパスとは**別のインスタンス
または別コンテナ**として分離して稼働」としている。現在 133.125.225.64 では
Canvas本体＋カスタム層＋PostgreSQL が動いている。ここに動画配信を伴う
eラーニングが同居すると、**CPU・メモリ・帯域・ディスクを奪い合う**。

- 望ましいのは**別インスタンス**。同一インスタンスに同居させるなら、
  リソース上限（`deploy.resources`）とディスク容量の事前見積りが要る
- サブドメインも別（例: `learn.ngas.jp`）。本リポジトリの独自ドメイン移行
  （手動対応リスト B3）と**まとめて決めた方がよい**

### 4.2 ノーティのリソース競合（スケジュール）

先方 第10章は「着手から検収まで**約5週間しかない**」「E4が遅れると納期全体が崩れる」
と自認しており、検収は **9月30日**。本リポジトリのノーティ納品分の受け入れテストは
**9月中下旬**で、完全に重なる。

**本リポジトリはSOFTDOINGの参照実装（バックアップ）であり、この競合そのものが
`CLAUDE.md` 10章が想定したリスク（過去の委託案件での要件未達）の再来になり得る。**
本リポジトリの完成度を上げておく判断は、この文脈でも正しい。

### 4.3 先方文書に残る前提のズレ（本リポジトリへ持ち込まない）

先方 1.3 の対象利用者に「中学生・高校生・大学生」、3.2 に「未成年が含まれる」とある。
これは eラーニング側の対象であり、**本リポジトリの授業の対象は企業・行政の社員（成人）**
で確定済み（`CLAUDE.md` 9章・パンフレットv2）。この前提は変えない。

ただしSSOで受講生マスタを共有する以上、**保管するデータ**に未成年が混ざり得る。
それが何を意味するかは 3.2.3 に整理した（結論: 機密性の水準は変わらず、
効くのはPマークの保護者同意運用）。

## 4.2 実装状況とAPI仕様（2026-09-01 E7-b・E7-c 実装済み）

先方へ渡す仕様はこの節が「正」。**認証は連携専用トークン1本**で、人のログイン
（LTI・ロールCookie）とは別系統。Canvasの管理者トークンは渡さない。

```
Authorization: Bearer <INTEGRATION_API_TOKEN>
```

トークンはサーバー側で発行し、口頭・チャットではなく安全な手段で受け渡す
（32文字以上。未設定の間は 503 を返す fail-closed。手動対応リスト参照）。

### E7-b `GET /api/integration/units` — 単元マスタの参照

```json
{ "units": [ { "id": "a1", "title": "お店の紹介文をAIに書かせよう",
               "deadline": "2027-03-31T23:59:00+09:00" } ] }
```

返すのは識別子・表示名・締切のみで**個人情報を含まない**ため監査ログには残さない。
相手が古い単元表を掴んだまま送ってこないよう `cache-control: no-store`。

### E7-c `POST /api/integration/mastery` — 自宅学習の到達度の受信

```json
{ "items": [
    { "studentId": "s1", "unitId": "a1", "score": 72,
      "reasons": ["第2章の誤答が多い"], "measuredAt": "2026-09-01T00:00:00Z" },
    { "studentId": "s2", "unitId": "a1", "score": null,
      "measuredAt": "2026-09-01T00:00:00Z" }
] }
```

| 項目 | 決まり |
|---|---|
| `score` | 0〜100の整数、**または `null`**。`null` は「測定中」で、**0点ではない**（先方E4例外1）。項目ごと省略は不可 |
| `reasons` | 文字列の配列（任意）。受講生本人の画面に表示される（先方 受け入れ基準 B-3） |
| `items` | 1〜500件／リクエスト |
| 再送 | 受講生×単元×送信元で**上書き**。同じ内容を再送しても増えない |
| 部分適用 | **しない**。1件でも不正なら全体を400で拒否する（何が入ったか分からなくなるのを防ぐ） |

応答:

| 状況 | 応答 |
|---|---|
| 受理 | `200 {"accepted": n, "savedAt": "..."}` |
| 入力不正 | `400 {"details":[{"index":0,"field":"score","message":"..."}]}` — **項目ごとに何が悪いかを返す**ので、直して再送できる（先方E7例外4） |
| 未知の単元ID | `409 {"unknownUnitIds":[...]}` — 単元マスタの「正」はこちら。E7-bを取り直して再送 |
| トークン不正 | `401` |
| トークン未設定（本リポジトリ側の設定漏れ） | `503` — 認証失敗と区別する |

受信は1リクエスト＝1件で監査ログに残す（受講生ID・単元ID・スコアのみ。**氏名は残さない**）。
退会者データ削除（F5②）で自宅学習の到達度も同時に消える。

**表示は 3.2.2 のとおり並置**。S5「自分の到達度」に「教室の到達度」とは別セクションで
出し、画面上にも「合算していません」と明記している。
