# BtoB研修の進行方針と全日程の教材再編計画

更新日：2026年10月6日

合意済みの基本方針を記録し、10日間の既存教材を再編するための作業一覧を示す。基本方針と、以下の具体的な運用案・編集案は区別する。本書の保存だけで公開教材、Canvas設定、正式な修了条件を変更しない。

## 合意した基本方針

受講管理側の5機能は、[システム開発コース開発タスク](SYSTEM_DEVELOPMENT_COURSE_TASKS.md)に登録。教材再編とは別の作業台帳で管理する。

1. 一人ひとりが、自社で最も困っていることを解決する別々のシステムを作る。機能を受講者へ割り当てたり、分担して一つのシステムを作ったりしない。
2. 共通事例は発想・判断の材料であり、同じアプリを再現する課題ではない。備品依頼、承認、検索、集計など、特定の機能を全員へ必須化しない。
3. 冒頭に必要事項を共有し、各自が教材を確認したら自分の開発へ進む。一律の「座学2時間＋開発2時間」は固定しない。
4. 教材は「全員に必要な要点」「必要な人向けの説明」「発展的な補足」に分ける。知識の完全定着や設計書提出を開発開始の条件にしない。
5. 講師は課題整理、個別相談、開発支援、安全上の確認を担う。全員が講師の説明終了を待つ進行にはしない。
6. 小テスト・誤答分析は授業外のEラーニングへ集約する。Eラーニングの完成・受講・点数を開校や対面開発の条件にしない。
7. Questは自社の困りごとを捉え直す体験に使う。企業別動画を毎期作らず、共通の体験から各自が気づきを得る。小テスト専用端末にはしない。
8. 合意した範囲のシステム完成を目指す。実データ投入・外部送信・本番公開は、教材読了とは別に安全確認と会社側の承認を行う。

## 一日の進め方の案

4時間枠を維持する。冒頭10〜15分に連絡・安全上の注意・今日のテーマを共有し、その後は教材確認と個別開発を並行する。最後15分に、動いたこと、困っていること、次の再開地点を整理する。

全員向け教材の目安は20〜40分程度から設計する。これは読了期限ではなく、説明を短く保つための編集目標。初日の準備やQuest初回説明には別途時間を確保する。機器の準備を待つ間はPC教材や開発を進められるようにする。

休憩を削って開発時間を増やさない。旧概要の休憩20分と現行原稿の30分に差があるため、正式な時間割・訓練時間の数え方は別途確定する。残り時間を各自の教材確認・相談・開発に充て、細かな開発工程を全員に指定しない。

教材の終わりには「自分のシステムに関係すること／今は不要なこと／相談したいこと」を考える短い問いを置く。採点や提出は要求せず、毎回全員が講師の許可を待つ関門にも使わない。実データや公開などの確認は別に扱う。

### 相談と進捗の把握

講師が把握するのは、解決したい困りごと、今日進めたいこと、現在の状態、支援が必要な点。運用案として「教材確認中・開発中・相談希望・今日はここまで」の区分を使う。新しい管理機能の実装は前提にせず、既存機能や学校が許可した管理表で試す。

相談待ちの人には、別の画面調整や確認など安全に進められる作業を一緒に決める。他社の困りごとの詳細や業務情報を共有画面へ載せない。共通の疑問が多い場合のみ、講師が短く全体説明する。

### 開発枠の共通ルール

日ごとのテーマは、全員の開発工程や機能を指定するものではない。本人の続きから進み、不要な機能をその日の教材のためだけに追加しない。困りごとが大きい場合は、本人と講師で役に立つ最初の範囲を決める。単に備品依頼へ題材を変更して間に合わせない。

公開教材へ実データを入力しないことと、自社の業務を題材にしないことは別である。実名や秘密情報を使わず、必要な構造を架空データで試す。資料や環境が不足した場合は支援課題として把握し、模擬演習の消化を自社システム完成の代わりにしない。

## 小テストとEラーニング

授業用の必須導線から診断・途中確認・最終小テスト・復習テストを外す計画とする。既存の問題、解説、答案、採用履歴は削除しない。Eラーニング側が未完成の間は、移管できたように表示しない。

| 対象 | 編集・設定計画 |
|---|---|
| STEP01 S06/S11/S18/S19と診断導線 | 問題・解説を移管候補として保管。授業時間割と受験指示から外す |
| STEP02〜04 B16/B17、STEP03〜04のその他の受験導線 | 最終・復習の受験を外す。有用な短い説明は参照教材へ残せる |
| STEP05 B11/B21/B23/B24と診断導線 | テスト部分を外す。B21の実演、B24の次回への引継ぎは残す |
| STEP06〜09 B05/B10/B16/B17と各診断導線 | 採点を伴う受験を外す。STEP09 B17などの説明・実演部分は作り直して残す |
| 本文以外のquiz設定、動画内の受験案内、ワーク、リンク | 一括で確認。本文から消しただけで移行完了にしない |
| Canvasの授業ホーム、小テスト一覧、モジュール等 | 後工程で受講者の必須導線を調整。今回は変更しない |
| Eラーニングへの移管 | 設問・正答・解説・単元タグ・版を対応付け、受信側仕様と権利・公開条件を確認してから実施。学習履歴の移送は別判断 |

授業中の問いかけやQuestの選択操作は、気づきのために必要なものだけ残す。点数、合否、ランキング、全問正解を次へ進む条件とする仕組みは付けない。Eラーニング側の個別誤答分析をCanvas側へ重複実装しない。

正式な修了判定には既存資料との不一致が残る。授業内小テストを外す合意だけで、既存の修了条件や出席条件まで変更済みとはしない。

## Quest教材の修正方針

既存の共通体験を優先して見直し、毎日の利用は義務化しない。自社課題へのインスピレーションを目的とし、模倣対象の完成アプリを提示する構成を避ける。PCで同等の内容を確認できる代替も残す。

10月6日の台本初稿 `work/quest-office-scenario-draft-20261006.md` は、改善フォームと特定機能の実装へ誘導するため、そのまま制作しない。次稿では「気づいた困りごと」「自社の最重要課題について得た視点」を終点にする。台本レビュー後に短い試作、Quest実機確認、全編制作の順で進める。

## 教材ページの共通構成案

1. 今日学ぶ視点と、開発にどう役立つか。
2. 全員が確認する短い説明と共通例。
3. 自分の課題について考える問い。該当しない場合は無理に当てはめない。
4. 自分の開発へ進む案内。講師の一斉進行を待たなくてよい。
5. 必要な説明を探せる補助教材。承認などの具体例はここに置く。
6. 相談方法と、次回の再開に必要な短い記録。

閲覧完了を出席・技能習得・公開承認の証明にしない。進捗記録機能の追加は、教室運用で不足が確認されてから判断する。

## 運用として残る決定

- 正式な修了条件と、パンフレット・要件・出席運用との整合。
- 休憩と授業時間の数え方、Quest準備・交代の時間。
- 講師人数と相談待ちの扱い、開校前に確保するBASE44環境・利用枠。
- 各受講者の事前ヒアリングから、本人が解決したい問題と研修内の範囲を合意する手順。
- Eラーニングの提供時期、利用条件、問題移管の担当。未提供のサービスを必須にしない。
