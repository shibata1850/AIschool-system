## Chapter 1 — Overview

### 1.1 Purpose

**To make learning work during the hours students cannot come to the classroom.**

Face-to-face classes alone (1–2 times a week) produce uneven retention between
students. This system is built so that asynchronous study at home or at work does
not end at "watched the video and moved on": **the AI identifies weak areas from
quiz results and selects which problems to serve next.**

This is also central to the business policy of making the learning-management
system an original in-house build rather than an off-the-shelf service. **Future
expansion into a system for junior-high and high-school cram schools will be built
on this foundation.**

### 1.2 Scope of business covered

Watching video material at home or at work; taking and auto-grading end-of-chapter
quizzes; AI estimation of mastery and selection of review questions; reporting
learning status to the student and to the corporate training manager; registration
of material and questions by instructors.

### 1.3 Intended users

| Category | Assumption | Main device |
|---|---|---|
| Students (school age) | Junior-high, high-school and university students. Preparation, review and self-study | Smartphone, iPad |
| Working adults | Individual enrolment. Study during commutes or in the evening | Smartphone, home PC |
| Corporate students | Employees under a corporate contract (assume 3–4 people per company). Study inside and outside working hours | Work PC, smartphone |
| Corporate training managers | HR / training staff who need to track the progress of the employees they enrolled | Work PC |
| Instructors | SOFTDOING staff. Register material and follow up students | Instructor machine, office PC |

### 1.4 Completion-criteria KPIs

This is a new system, so there is no "before" baseline. Meeting the following
figures after go-live is the completion condition.

| # | Indicator | Completion condition | Measurement |
|---|---|---|---|
| 1 | Self-sufficiency | A student reaches their first video view and first quiz submission **within 10 minutes of first login, without asking anyone** | Measured with 3 test subjects (one school-age, one working adult, one senior) |
| 2 | Automated mastery assessment | **Zero hours per week** of manual tallying by instructors. Mastery per unit is calculated automatically per student | Confirm automatic weekly report generation during acceptance testing |
| 3 | Review-selection accuracy | **At least 80%** of the next review questions come from units the student answered incorrectly in their most recent quiz | Judged by injecting 20 test records during acceptance testing |
| 4 | Mobile-complete | The full loop — watch → take quiz → check result → review — can be completed **on a smartphone alone** | Verified on one physical iOS device and one Android device |

## Chapter 2 — Boundary with Cloud Campus (most important)

This system and "Cloud Campus" (purchase order SD-2026-0720-001, funded under a
different subsidy programme) are **separate systems accounted for under separate
subsidies**. Overlapping functionality will be flagged as double-counting in the
performance report. The boundary is defined below, and **the contractor shall not
implement across this boundary.**

### 2.1 Division of roles

| Aspect | Cloud Campus | **e-Learning system (this document)** |
|---|---|---|
| Where learning happens | Face-to-face in the classroom | Asynchronous, at home or at work |
| Synchronous / asynchronous | Synchronous (instructor present) | Asynchronous (student chooses the time) |
| Platform | Canvas LMS open-source edition + custom layer | **Independent web application (no Canvas dependency)** |
| Main features | Course management, material delivery, AI-tutor integration, Jupyter exercises, prompt exercises, in-class progress monitoring | Video-viewing management, automatic quiz grading, AI mastery analysis, review selection, learning-report delivery |
| Target devices | Classroom NUCs, Meta Quest 3, NearHub, iPad | Smartphone, tablet, home / work PC |
| Unit of evaluation | Grading and rework per exercise assignment | Mastery score and weakness detection per unit |

### 2.2 Features that must NOT be implemented in this system (they belong to Cloud Campus)

- Course / class / timetable management (**the master data lives on the Cloud Campus side**)
- AI-tutor conversation (Cloud Campus F2)
- Jupyter Notebook exercise runtime
- Prompt-exercise delivery and first-pass AI grading (Cloud Campus F3)
- Real-time in-class progress monitoring (Cloud Campus F4)
- Anything related to VR / MR display or delivery

### 2.3 Direction of integration

```
  [Cloud Campus]                          [e-Learning system]
   Canvas LMS + custom layer               Independent web app
   - Student master (source of truth) --SSO-->  - Log in with the same ID
   - Course / unit master (truth)     --API-->  - Reference units
   - Mastery dashboard                <--API--  - Send home-study mastery scores

  The student master and the unit master are owned by Cloud Campus.
  This system holds no master data; it only references and returns scores.
```

This design avoids the situation where a student has two separate accounts. It also
makes it possible to demonstrate in the performance report that there is no
functional overlap.

## Chapter 3 — Constraints

### 3.1 Operating environment

| Item | Content |
|---|---|
| Hosting | **Sakura Cloud**, on the client's account. Runs **separated from Cloud Campus, as a separate instance or separate container** |
| Contract holder / cost | SOFTDOING Inc. (the client). The client issues the working accounts |
| Domain | A **separate subdomain** from Cloud Campus (e.g. `learn.ngas.jp`). DNS is managed by the client |
| SSL/TLS | TLS 1.3. The contractor performs certificate issuance and auto-renewal setup |
| Backup | Daily full backup, **14 generations retained**. Restore procedure demonstrated during acceptance testing |
| Monitoring | Uptime monitoring, 24 hours. The client specifies the alert destination |

### 3.2 User constraints

- **Devices**: smartphone is primary, PC secondary. **No native app** — must run in a browser
- **Network**: home and mobile lines. **Video viewing must work at an effective 10 Mbps**
- **Literacy**: from junior-high students to seniors. Technical terms must be accompanied by plain-language equivalents
- **Study time**: assume fragmented sessions of **15–30 minutes**
  → **Playback position and partially-entered answers must not be lost when the student closes the app mid-way**
- **Minors are included.** Learning logs are treated as sensitive personal data

### 3.3 Integration with existing systems

| Target | Treatment |
|---|---|
| Cloud Campus (Canvas LMS) | **Integrate.** SSO (shared student accounts), unit-master reference, mastery-score return |
| Accounting / invoicing | No integration |
| Notification to guardians | Out of scope for this phase (to be considered when expanding to secondary education) |

### 3.4 Handling of video material

**Production, filming and editing of the video files themselves are out of scope
for this order** (the client provides them). This system is responsible for
registering videos with the delivery platform and recording viewing progress.
The delivery method — self-hosted storage or an embedded external video service —
is to be proposed by the contractor including monthly running cost, and selected
by the client.

## Chapter 5 — Functional specification (5W1H + exceptions)

### E1 — Student portal

| | |
|---|---|
| **Who** | Students (school-age, working adults, corporate) |
| **When** | Any time. Assume fragmented sessions of 15–30 minutes |
| **Where** | Smartphone primarily; tablet and PC also. Runs in a browser |
| **What** | Today's task, progress per unit, resume-where-you-left-off, most recent weak areas |
| **Why** | **Do not make the student think about "what should I do?" The moment they hesitate, learning stops** |
| **How** | Present exactly **one** "next thing to do" on the first screen after login. **Do not present a list of options** |

**Exception cases**

1. Student opens a learning URL while logged out → return them to the original URL after login
2. Previous session was left unfinished → show "resume" with top priority
3. All units are complete → offer review of weak units (**never show an empty screen**)
4. Connection lost → do not blank the screen; show a prompt to reconnect

### E2 — Video viewing management

| | |
|---|---|
| **Who** | Students |
| **When** | At home, at work, while travelling |
| **Where** | Smartphone, tablet, PC |
| **What** | Video playback, recording of viewing progress and playback position, completion判定 |
| **Why** | Eliminate "I think I watched it" and make E4's input data accurate |
| **How** | Record playback position at regular intervals. **Cumulative playback time ≥ 90% of the video length counts as complete** |

**Exception cases**

1. Student closes the screen mid-way → keep the playback position and resume from the same point next time
2. **Playback speed** → allowed, but **cumulative time is counted against the video's nominal length, not wall-clock time**
3. Student skips ahead → **skipped ranges do not count toward completion**
4. Low bandwidth → automatically reduce quality and continue playback. If playback is impossible, allow the student to add it to "watch later"
5. **Simultaneous viewing on multiple devices with the same account** → the value from the most recently updated device wins

### E3 — Quiz feature

| | |
|---|---|
| **Who** | Students (taking); instructors (registering questions, reviewing results) |
| **When** | After completing each chapter's video, and during review |
| **Where** | Smartphone primarily |
| **What** | End-of-chapter delivery, automatic grading, explanation display, accumulation of wrong answers |
| **Why** | Capture retention as a number. This is E4's input data |
| **How** | Three question types: single-choice, multiple-choice, fill-in-the-blank (exact match). **Grading is instant.** Wrong answers accumulate with a unit tag |

**State transitions (one quiz)**

```
[Not taken] --start--> [In progress] --submit--> [Graded] --view explanation--> [Done]
                 |                                    |
            interrupt (kept)                       retake
                 |                                    |
                 \--> [In progress (resumable)]       \--> [In progress]
```

**Exception cases**

1. Student leaves mid-answer → answer state is kept and can be resumed
2. **Retaking the same quiz** → allowed. The latest result is reflected in mastery; **all history is retained**
3. Immediate retake after a perfect score → not restricted, **but the first attempt is weighted more heavily** in the mastery score
4. A question is found to be wrong (e.g. the marked correct answer is incorrect) → the instructor can **disable the question**, and grading results containing it are **recalculated**
5. Submission fails due to lost connection → answers are held on the device and sent on reconnect

### E4 — AI mastery analysis engine

| | |
|---|---|
| **Who** | Students (see their results); instructors (see class-wide trends) |
| **When** | On every quiz submission (immediately) and as a weekly batch |
| **Where** | Student portal, instructor screen |
| **What** | Estimation of mastery score per unit, extraction of weak units, selection of the next review questions |
| **Why** | **The differentiator of this system. It turns "watched the video and finished" into "closed the gap and finished"** |
| **How** | Inputs: viewing-completion rate, quiz accuracy, distribution of wrong answers across units, elapsed days. Output: mastery 0–100 per unit. Review questions are drawn from units below a threshold |

**Conditions on the calculation method**

The mastery algorithm is **proposed by the contractor and approved by the client**.
The approved logic must be **written explicitly into the specification; the
contractor shall not deliver it as a black box.** Weighting coefficients must be
changeable from a configuration file or an admin screen.

**Exception cases**

1. Student with little data (fewer than one attempt) → display **"measuring"**. **Do not treat as zero**
2. Long absence → decay mastery according to elapsed days (reflecting forgetting). **The decay rate must be a configurable value** so it can be tuned after launch
3. All units above threshold → offer review starting from the oldest studied unit
4. **Failure of an external AI API** → fall back to the default statistical logic (accuracy-based). **Analysis must not stop**
5. Student disputes the result → **the student must be able to see the basis of the score** (which wrong answers affected it). It must not be a black box

### E5 — Learning-report delivery

| | |
|---|---|
| **Who** | The student; the corporate training manager |
| **When** | Weekly (day and time configurable by an administrator) |
| **Where** | Email, and displayed in the portal |
| **What** | Study time this week, units completed, quiz results, change in mastery, recommended units for next week |
| **Why** | **Corporate enrolment creates accountability to the training manager. Reduce manual reporting to zero** |
| **How** | Generated as a batch and sent to the student and to the training manager of the company the student belongs to |

**Exception cases**

1. **Zero study activity this week** → send it anyway, as "no study". **Do not skip sending**
2. Individual (non-corporate) student → send to the student only; there is no corporate manager
3. Multiple training managers at one company → must support multiple recipients
4. Student requests to stop delivery → **the student's own copy can be stopped. The manager's copy cannot**, because it is based on the corporate contract. **This must be stated to the student at enrolment**
5. Batch fails → notify an administrator and provide a route to re-run it manually

### E6 — Content management

| | |
|---|---|
| **Who** | Instructors, administrators |
| **When** | Before the course opens, and on an ongoing basis |
| **Where** | Office PC, instructor machine |
| **What** | Video registration, assignment to units, question registration and unit tagging, publish / unpublish |
| **Why** | **So the client can operate independently without asking the contractor to add material** |
| **How** | Registered from an admin screen. Questions also support **bulk CSV import** |

**Exception cases**

1. A published question is edited → **existing results are not recalculated**; the edited question applies from the next attempt onward
2. A video is replaced → the instructor can choose whether to reset viewing progress
3. A unit is deleted → **past learning history is retained**; it is only excluded from aggregation
4. CSV import contains malformed rows → report errors per row, and let the operator choose between importing only the valid rows or aborting entirely

### E7 — Cloud Campus integration

| | |
|---|---|
| **Who** | All users (transparently) |
| **When** | At login, when referencing the unit master, when returning mastery scores |
| **Where** | Server-to-server |
| **What** | SSO, unit-master reference, return of mastery scores calculated by this system to Cloud Campus |
| **Why** | So students do not hold two accounts, and instructors can see everything on one screen |
| **How** | SSO via **LTI 1.3 or OAuth 2.0**. Master reference and score return via **REST API** |

**Exception cases**

1. **Cloud Campus is down** → this system continues to operate standalone. **Mastery-score returns are queued and sent after recovery**
2. A student is deleted on the Cloud Campus side → **disable the account in this system too.** Learning history follows the retention rules
3. The unit master changes → this system's references update automatically. **Differences are logged** so an administrator can review them
4. A returned mastery score is rejected by Cloud Campus → notify an administrator, and allow re-sending

## Chapter 6 — Permissions, audit and personal data

### 6.1 Permission matrix

| Operation | Administrator | Instructor | Student | Corporate training manager |
|---|---|---|---|---|
| Watch videos / take quizzes | ○ | ○ | ○ | − |
| View own mastery | ○ | ○ | ○ | − |
| View mastery of assigned students | ○ | ○ | − | **○ (own company's students only)** |
| **View students of other companies** | ○ | − | − | **−** |
| Register / edit material and questions | ○ | ○ | − | − |
| Change mastery-calculation settings | ○ | − | − | − |
| User management | ○ | − | − | − |
| View audit log | ○ | − | − | − |

> **The fact that a corporate training manager cannot access another company's
> student information is a MANDATORY E2E test item. Mixing information between
> client companies would be a serious business incident.**

### 6.2 Audit log

- **Coverage**: creation, update and deletion of all data (operator, timestamp,
  before / after values). **Question edits and changes to mastery settings must
  always be recorded**
- **Read permission**: administrators only
- **Tamper resistance**: the log table is **append-only from the application**
  (no UPDATE / DELETE privilege granted)
- **Retention**: same rule as Cloud Campus (proposed: while enrolled + 3 years
  after graduation; to be aligned with the client's personal-information policy)

### 6.3 Personal data

- **Students include minors.** Learning logs and answer content are treated as
  **sensitive personal data**
- **Real data must not appear** in development environments, test data, log output
  or commits. **Test data must be fictional only**
- When using an external AI API, **remove names, contact details and affiliation**
  from the transmitted data
- Information disclosed to a corporate training manager is **limited to the
  learning records of students belonging to that company**

## Chapter 7 — Data model (initial draft)

Entities: student / company / corporate training manager / unit / video material /
question / choice / attempt session / answer / mastery score / viewing progress /
review queue / report-delivery history / audit log.

contact details are **owned by Cloud Campus**; this system holds only the minimum
needed for display.

## Translator's notes (not part of the original)

Points worth flagging to whoever works from this translation:

1. **Chapter 11 item 5 is unresolved and it is the core of the system.** E4 cannot
   be built to specification until the mastery algorithm is approved. Propose an
   approach early; do not start coding a guessed formula.

   mastery must be **nullable** ("measuring", not zero, for students with too

   it is. Design the data model for both from the start.

   mandatory test item.** Treat it as a first-class requirement, not an
   afterthought.
4. **Chapter 8 C-7** requires demonstrating that Cloud Campus features are *not*
   present. Keep the boundary in chapter 2.2 visible while working.
