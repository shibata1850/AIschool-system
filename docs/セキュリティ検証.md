# セキュリティ検証（F5③ 脆弱性スキャン）

- 対応する受け入れ基準: 要件定義書 9.2 **F5③ 脆弱性スキャンで Critical/High 0件**
- 検証ツール: Trivy（コンテナイメージの脆弱性スキャン）
- 対象: カスタム層アプリのイメージ（`custom-layer-app`）と `postgres:16-alpine`
- 実施環境: さくらのクラウド 本番サーバー
- **現状（2026-08-31）: app イメージ Critical 0 / High 0 を達成。
  `postgres:16-alpine` の24件は上流イメージの中身で、alpine継続を確定（2.4）**

---

## 1. 2026-08-31 の測定と分析

### 1.1 測定結果（対策前）

| 対象 | Critical | High | 合計 | うち修正版あり |
|---|---|---|---|---|
| app イメージ | 4 | 58 | 62 | **62（全件）** |
| `postgres:16-alpine` | 1 | 23 | 24 | **24（全件）** |

**全件に修正版が存在する。**「上流が直していないので対応不能」という指摘は1件もない。

### 1.2 由来別の内訳（app イメージ）

| 由来 | 件数 | 実体 |
|---|---|---|
| `lang-pkgs` の `stdlib` | Critical 3 / High 46 = **49** | **esbuild の Goバイナリ**に埋め込まれた Go 標準ライブラリ |
| `lang-pkgs` のnpmパッケージ | 約11 | `tar` C1/H2、`brace-expansion` H3、`pacote` H2、`sigstore` H1、`picomatch` H1、`ip-address` H1 |
| `os-pkgs`（Alpine） | High 2 | `libssl3` / `libcrypto3`（修正版 3.5.8-r0） |

### 1.3 原因 — 本番イメージに開発用パッケージが入っていた

`Dockerfile` の最終ステージが `COPY --from=builder /app ./` で、ビルド段階の
`node_modules` をまるごと本番イメージへ持ち込んでいた。その結果
`@playwright/test`・`vitest`・`typescript`・`drizzle-kit`・`tsx` とその依存ツリーが
本番に同梱されていた（`node_modules` 631.6MB）。**本番では1行も実行されない。**

esbuild は Go で書かれており、これらの devDependencies が **5コピー**引き込んでいた:

```
drizzle-kit  → @esbuild-kit/core-utils → esbuild 0.18.20  ← 古い。Criticalの主因
drizzle-kit  → esbuild 0.25.12
tsx          → esbuild 0.28.2
vitest       → vite → esbuild 0.28.2
```

**`stdlib` 49件はここ由来。** また `tar`・`pacote`・`sigstore`・`brace-expansion`・
`picomatch`・`ip-address` は、いずれも**本番依存ツリーには存在しない**
（本番依存は `@anthropic-ai/sdk` / `drizzle-orm` / `jose` / `next` / `pg` /
`react` / `react-dom` の7つだけ）。devDependencies かベースイメージ同梱の npm CLI 由来。

> **本リポジトリのアプリケーション依存そのものには Critical/High が1件も無い。**
> 検出されていたのは、本番に入れるべきでなかったものと、ベースイメージの中身だった。

## 2. 対策（2026-08-31 実施）

### 2.1 イメージから開発用パッケージを外した

`Dockerfile` を次のとおり変更した。

1. 運用スクリプト（`scripts/migrate.ts` / `seed.ts` / `generate-weekly-report.ts`）を
   **ビルド時に esbuild で素のJSへコンパイル**し `dist-scripts/` へ出力する。
   外部依存は `pg` と `drizzle-orm` だけになり、実行時に `tsx` が要らなくなる
   （`migrate.ts` は元から `drizzle-orm/node-postgres/migrator` を使っており、
   `drizzle-kit` も実行時には不要）
2. `npm prune --omit=dev` で開発用パッケージを落とす
3. 最終イメージへは `node_modules` / `.next` / `dist-scripts` / `drizzle` /
   `package.json` のみをコピーする（`src/`・`e2e/`・テスト設定は入れない）

**運用コマンドが変わる**: コンテナ内では `npx tsx scripts/xxx.ts` ではなく
`node dist-scripts/xxx.mjs` を使う（`infra/custom-layer/README.md`・手動対応リスト B14）。

### 2.2 本番サーバーでの実測（2026-08-31）

対策後のイメージをデプロイし、実サーバーで確認した結果:

| 確認項目 | 対策前 | 対策後 |
|---|---|---|
| `vitest`/`typescript`/`tsx`/`drizzle-kit` の同梱 | あり | **なし** |
| **esbuild の Goバイナリ数** | 5 | **0** |
| `node_modules` サイズ | 631.6MB | **498.8MB** |
| コンパイル済み `generate-weekly-report.mjs` の実行 | — | 成功（通知: 送信済み 1名） |
| cron の `npx tsx` 参照 | 1行 | **0行**（`node dist-scripts/*.mjs` へ移行済み） |

**Trivy再測定の結果（同日）**:

| 対象 | 対策前 | 対策後 |
|---|---|---|
| app | Critical 4 / High 58（62件） | **Critical 1 / High 12（13件）** |
| `postgres:16-alpine` | Critical 1 / High 23（24件） | Critical 1 / High 23（**変化なし**） |

**app は49件減。予測どおり `stdlib`（esbuildのGoバイナリ）が丸ごと消えた。**

### 2.3 残った13件の正体と、その除去（第2弾）

| 由来 | 件数 | 内訳 |
|---|---|---|
| npm CLI 同梱の依存（`lang-pkgs`） | Critical 1 / High 10 | `tar`（C1/H2）・`brace-expansion`（H3）・`pacote`・`sigstore`・`picomatch`・`ip-address` |
| Alpine OSパッケージ（`os-pkgs`） | High 2 | `libssl3` / `libcrypto3` |

`tar`・`pacote`・`sigstore` 等は**ベースイメージが同梱する npm CLI 自身の依存**で、
本リポジトリの依存ツリーには存在しない。`docker build --pull` しても、上流の
`node:22-alpine` が古い npm を同梱している限り消えない。

**このイメージで npm が必要なのは起動コマンド（`npm start`）だけ**だった
（cron・マイグレーションは既に `node dist-scripts/*.mjs` へ移行済み）。
そこで次の2点を追加した:

1. `RUN apk upgrade --no-cache` — OSパッケージを更新（`libssl3`/`libcrypto3`）
2. `RUN rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/npm /usr/local/bin/npx`
   — npm CLI ごと削除。起動は `CMD ["node", "node_modules/next/dist/bin/next", "start"]`

**結果（2026-08-31・本番サーバー実測）: app イメージ Critical 0 / High 0。**
Trivyの出力に `Total:` 行が出ず、全パッケージが `0`（Clean）と判定された。

ビルドログで対策の効果を確認できる:

- `apk upgrade`: `libcrypto3` / `libssl3` を 3.5.7-r0 → **3.5.8-r0** へ更新
- npm削除: `npm removed: YES`（`/usr/local/bin/npm` が存在しない）
- 新しい起動方法: `Ready in 189ms` → ローカル疎通 **200**
- `node dist-scripts/generate-weekly-report.mjs`: 生成・通知とも成功

> **`F5③ 脆弱性スキャンで Critical/High 0件` は、appイメージについて達成した。**
> 残るのは `postgres:16-alpine`（2.4）のみ。

### 2.4 `postgres:16-alpine` — **alpine継続で確定（2026-08-31）**

24件（Critical 1 / High 23）は**対策前後で変化しなかった**。`docker compose pull db`
で最新を取得済みなので、**現時点の公式イメージがこの状態**ということになる。
検出のほとんどはGo標準ライブラリ（`net/http`・`crypto/tls`・`encoding/xml` 等）で、
イメージが同梱するGoバイナリ由来。

**Debian版（`postgres:16`）と実測比較した結果、alpine継続が明確に有利だった:**

| イメージ | OSパッケージ | 言語パッケージ（Goバイナリ） | 合計 | サイズ |
|---|---|---|---|---|
| `postgres:16`（Debian） | C13 / H38 = 51 | C1 / H21 = 22 | **C14 / H59 = 73** | 642MB |
| **`postgres:16-alpine`（現行）** | C0 / H2 = 2 | C1 / H21 = 22 | **C1 / H23 = 24** | 420MB |

**注目すべきは言語パッケージ側が両者で完全に一致していること**（どちらも C1 / H21 = 22）。
これは**公式イメージが両方の版に同じGoバイナリ（`gosu` 等の権限降格ツールと見られる）を
同梱している**ことを意味する。よってDebian版へ移行しても当該22件は解消せず、
**OS由来の脆弱性を49件増やすだけ**になる。

**結論: `postgres:16-alpine` を継続し、残る24件は根拠を添えて報告書に記載する**
（3章の判断基準3）。報告書に載せる根拠:

1. 本リポジトリ側に手が無い（上流公式イメージの中身）
2. **Debian版は3倍悪い**（73件）。イメージ選択として現行が最善であることを実測で確認済み
3. 該当のGoバイナリはコンテナ起動時の権限降格にのみ使われ、
   ネットワークに露出しない。DBコンテナ自体も `expose` のみでホストに公開していない
   （`docker-compose.yml`。同一Docker networkの app からのみ接続可能）
4. 公式イメージの更新は継続的に取り込む（`docker compose pull db` を定期実行に入れる）

> 参考: `gosu` 等の具体的なファイルパスの特定は未実施（Trivyの `Target` 抽出が
> 空振りした）。受け入れ時に必要なら `trivy image --format json` の
> `Results[].Target` で確認できる。

### 2.5 検証（2026-08-31・開発環境）

Docker Hub がサンドボックスのプロキシで遮断されているためイメージ自体はビルドできず、
**最終イメージと同一構成（本番依存のみ）をローカルに再現して**確認した。

| 確認項目 | 結果 |
|---|---|
| `vitest` / `typescript` / `tsx` / `drizzle-kit` / `esbuild` の除去 | すべて除去された |
| **esbuild の Goバイナリの残存数** | **0**（対策前は5） |
| `tar`・`pacote`・`sigstore`・`brace-expansion`・`picomatch`・`ip-address` の残存 | **すべて0箇所** |
| `node_modules` サイズ | 631.6MB → 499MB |
| `next start` の起動と応答 | 200 OK。権限外URLは403（fail-closed）も維持 |
| コンパイル済み `migrate.mjs` | マイグレーション適用に成功 |
| コンパイル済み `generate-weekly-report.mjs` | レポート生成に成功 |
| コンパイル済み `seed.mjs` | `--force` なしで正しく中止（安全弁が生きている） |

> `@playwright/test` の空ディレクトリと `playwright-core` は残る。これは
> **Next.js 16 自身の依存**であり devDependency ではないため `prune` では消せない。
> Goバイナリを含まないので `stdlib` 49件には無関係。

### 2.6 ベースイメージについて（当初の見立て）

`libssl3` / `libcrypto3`（High 2）と、npm CLI 同梱パッケージ由来の分は
**ベースイメージの中身**。対策は `docker build --pull` で
`node:22-alpine` の最新版を取り直すこと。`postgres:16-alpine` の24件も同様で、
`docker compose pull db` で最新を取得する（このイメージは頻繁に再ビルドされている）。

`postgres:16-alpine` の `lang-pkgs` 側は、公式イメージが同梱する `gosu`
（Goバイナリ）由来と見られる。これもイメージ更新で解消する見込み。

## 3. F5③ の受け入れ基準について

**「Critical/High 0件」は達成可能な目標であり、基準を緩める必要はない。**
**app イメージについては実際に 0件を達成した（2026-08-31）。**

当初、検出の大半が「上流未修正のOSパッケージ」だろうと想定して基準の見直しを
提案したが、実測の結果その想定は誤りだった。全件に修正版があり、かつ大半が
「本番に入れるべきでなかったもの」に起因していた。

再測定でなお残るものが出た場合に限り、次の順で判断する:

1. 修正版があるものは適用する（イメージ更新・依存更新）
2. 修正版がなく、かつ本番の実行経路に無いもの（開発用ツール等）は**イメージから外す**
3. 1・2のいずれも取れないものだけを、根拠を添えて報告書に残す
   （先方のeラーニング要件定義書 C-6 も「重大な指摘が**是正済み**」という基準）
