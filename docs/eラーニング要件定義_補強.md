## 1. なぜ補強が要るのか — 第1版に無いもの

第1版は機能仕様（E1〜E9）・受け入れ基準・データモデルがよく整理されている。
一方で、**「なぜこれを作るのか」を外部に説明するための記述が無い**。
補助金の実績報告と検収の両方で問われる箇所なので、発注者側で埋める。

| # | 第1版に無いもの | なぜ要るか |
|---|---|---|
| ① | **賃上げ補助金の趣旨との接続** | 第1版に「賃上げ」の語が一度も出てこない。**実績報告で「この投資がどう賃上げに資したか」を必ず問われる**。ここが空白のまま検収すると、後から書けなくなる |
| ② | **なぜ既製サービスを買わずに自社開発するのか** | 第1版1.1は「既製サービスではなく自社開発のオリジナルにする」と方針だけ述べ、**理由が無い**。補助金では「なぜ購入でなく開発か」が典型的な確認事項 |
| ③ | **2システムを合わせて何が実現するのかという積極的な定義** | 第1版2章は「重複しない」という**消極的な線引きだけ**。受講生から見た一つの学習体験としての姿が書かれていない |
| ④ | **事業計画上の位置づけ（数値）** | 受講者数・単価・売上の見通しが無い。KPIは「システムが動くか」の指標であって、**事業として成立するかの指標ではない** |

## 2. 背景

### 2.1 事業としての背景

Next Gen AI School は2026年10月開校の、企業・行政の社員向け人材育成プログラムである
（岩手県北上市・北上駅前）。通学制40時間（1日4時間×10日）で、受講生が**自社の業務課題を
BASE44により本番稼働システムとして1本完成させる**ことをゴールとする。

この対面プログラムを支える基盤が「クラウドキャンパス」（Canvas LMS＋カスタム層、
新事業進出補助金枠）である。**本システム（eラーニング）は、その対面時間の外側を埋める。**

### 2.2 なぜ今、非同期学習が要るのか

対面は週1〜2回・1日4時間である。**受講生の定着は対面時間の長さではなく、
対面と対面の間に何をしたかで決まる。** 第1版1.1が指摘するとおり、
この間を放置すると受講生ごとに定着差が開く。

さらに本校の受講生は**就業しながら学ぶ社会人**である。まとまった学習時間を取れず、
1回15〜30分の細切れ学習が現実的な形になる（第1版3.2）。
**この形に耐える仕組みは、対面授業用のLMSでは提供できない。**

### 2.3 なぜ既製サービスではなく自社開発なのか

第1版1.1の方針に、発注者として理由を与える。

1. **本校のカリキュラムが既製品の想定と違う。** 一般的なeラーニング製品は
   「決まった教材を順に消化させる」設計である。本校は受講生ごとに**題材（自社の業務課題）が
   違い**、到達度も単元別に分かれる。既製品の進捗管理はこの形に合わない
2. **クラウドキャンパスとのSSO・単元マスタ共有・到達度返送（E7）が要る。**
   既製SaaSでこの3点を同時に満たすものは現実的に見当たらず、満たせても
   **受講生が2つのアカウントを持つ**形になり、第1版2.3が避けようとした事態を招く
3. **将来の中学・高校向け学習塾システムへの展開の土台にする**（第1版1.1）。
   既製SaaSを借りている限り、この展開で毎月の利用料を払い続けることになる
4. **学習ログを自社で保持できる。** 受講生は企業・行政の社員であり、
   学習ログは要配慮の個人データとして扱う。外部SaaSに預けると、
   保持期間・削除・開示請求の運用を相手の仕様に合わせることになる

> 【要確認 A】補助金の実績報告で「購入ではなく開発を選んだ理由」を問われた際、
> 上記4点で足りるか。事務局に確認したい論点があれば追記する。

### 2.4 賃上げ補助金の趣旨との接続【要確認・最重要】

本システムは**岩手県中小企業賃上げ補助金**（交付決定 2026年7月10日付 岩手県指令経支第
280-19号）で計上する。**第1版には賃上げに関する記述が一切ない。**

補助事業として説明が成立する筋道は、現時点で次の2通りが考えられる。

| 筋道 | 内容 |
|---|---|
| **(a) 生産性向上による原資確保** | 講師の手集計・進捗管理・レポート作成の工数をゼロにし（KPI#2）、同じ人員でより多くの受講生を扱えるようにする。**創出した粗利を賃上げの原資にする** |
| **(b) 事業拡大による雇用・処遇改善** | 非同期学習の提供により受講可能な層（遠方・多忙・学生）を広げ、売上を伸ばす。**それを従業員の処遇改善に充てる** |

> 【要確認 B】**交付申請時にどちらの説明で出しているか**を確認したい。
> 賃上げ率のコミット（何%を、いつまでに、誰に対して）も、申請書に記載があるはずである。
> **本書の目的・KPIは、その申請内容と一致させる必要がある。**
> ここが食い違うと、システムが仕様どおり完成しても実績報告で説明できない。

### 2.5 二重計上の回避（第1版2章の再掲・遵守事項）

第1版が「本書の最重要事項」として明記するとおり、クラウドキャンパスと機能が重なると
**実績報告で二重計上と判断される**。両者は別の補助金で計上する別システムである。

発注者としても次を守る。

- クラウドキャンパス側（本リポジトリ）に eラーニングの機能を実装しない
  （`CLAUDE.md` 13.1 に規約として明文化済み）
- **逆も同じ。** 本システムに、第1版2.2が挙げるクラウドキャンパス側の機能
  （コース・時間割管理、AI講師対話、Jupyter演習、プロンプト演習、
  リアルタイム進捗モニタリング、VR/MR）を実装させない
- E7連携の「受け側」実装（到達度受信API等）は**クラウドキャンパスの
  ダッシュボードの入力を増やす実装**であり、eラーニングの機能ではない。
  この区別を報告時に説明できるようにしておく（`docs/eラーニング連携.md` 3.2.1）

## 3. 目的

### 3.1 三層に分けて定義する

第1版1.1は目的を1段落で述べている。実績報告と検収で使えるよう、階層に分ける。

```
[事業目的]   生産性向上と事業拡大により、賃上げの原資を確保する    ← 補助金に対する説明
     ↓
[サービス目的] 受講生の定着差をなくし、対面40時間の価値を最大化する  ← 受講生・受講企業に対する説明
     ↓
[システム目的] 非同期学習を「動画を見て終わり」にせず、
              弱点を特定して次の一手を出し分ける                  ← 開発に対する指示
```

### 3.2 事業目的

**生産性向上と事業拡大により、賃上げの原資を確保する。**（2.4 の【要確認 B】確定後に確定）

- 講師の手集計工数をゼロにする（第1版 KPI#2）ことで、**同一人員で扱える受講生数を増やす**
- 非同期学習の提供により、**通学だけでは受講できない層**（遠方・多忙・学生）へ広げる

### 3.3 サービス目的

**受講生の定着差をなくし、対面40時間の価値を最大化する。**

本校のゴールは「受講生が自社の業務システムを1本完成させる」ことである。
対面で作り切るには、**対面の間に前提知識が定着していること**が要る。
本システムは対面授業の代替ではなく、**対面を成立させるための下地**である。

あわせて、企業受講では**受講担当者への説明責任**が発生する。
週次レポートの自動配信（E5）は、この説明責任を手作業ゼロで果たすためのものである。

### 3.4 システム目的

**非同期学習を「動画を見て終わり」にせず、弱点を特定して次の一手を出し分ける。**（第1版1.1）

差別化の核はE4（AI習熟度分析）である。第1版10章も「E4が遅れると納期全体が崩れる」と
自認しており、**ここが本システムの価値そのもの**である。

### 3.5 目的と機能の対応

第1版のE1〜E9が、どの目的に紐づくかを示す。**目的に紐づかない機能は作らない。**

| 機能 | 紐づく目的 | 無いとどうなるか |
|---|---|---|
| E1 受講生ポータル | サービス目的 | 「何をすればいいか」で迷い、そこで学習が止まる |
| E2 動画教材の視聴管理 | システム目的 | E4の入力データが不正確になり、習熟度分析が成立しない |
| E3 小テスト | システム目的 | 同上。定着度を数値で捉えられない |
| **E4 AI習熟度分析** | **システム目的（核）** | **「動画を見て終わり」になる。本システムを作る理由が消える** |
| E5 受講レポート配信 | サービス目的・事業目的 | 企業への説明が手作業になり、講師工数ゼロ（KPI#2）が崩れる |
| E6 教材コンテンツ管理 | 事業目的 | 教材追加のたびに受注者へ依頼が要り、運用コストが残り続ける |
| E7 クラウドキャンパス連携 | サービス目的 | 受講生が2アカウントを持ち、講師が2画面を見ることになる |
| E8 テスト・品質保証 | （全体） | 検収できない |
| E9 ドキュメント・操作指導 | 事業目的 | 発注者が自力運用できず、外注依存が続く |

## 4. 発注者から見た優先順位

第1版11章の未決事項#2（納期の成立性）に対する、発注者側の考え方。

**着手から検収まで約5週間しかない。** 全部が揃わないリスクに備え、
**落としてよい順序**を先に決めておく。

| 優先度 | 機能 | 理由 |
|---|---|---|
| **絶対** | E4（AI習熟度分析） | 本システムの存在理由。これが無いなら既製品でよい |
| **絶対** | E1・E2・E3 | E4の入力を作る。これが無いとE4が動かない |
| 高 | E5（受講レポート配信） | KPI#2（講師工数ゼロ）に直結。企業受講の説明責任 |
| 高 | E6（教材管理） | 開講に間に合わないと、教材追加のたびに外注が要る |
| **段階リリース可** | E7（クラウドキャンパス連携） | 無くても本システム単体で動く。**ただしSSOが無いと受講生が2アカウントになる**ため、開校までには要る |

> 【要確認 C】上表の優先順位で、受注者と合意できるか。
> 第1版11章#2の代替案（E1〜E3を先行リリースし、E4以降を10月へ）は、
> **E4を後回しにする案なので発注者としては受け入れがたい**。
> 遅らせるならE5〜E7の側にしたい。
